# Harnesses

A harness is a coding agent surface, such as Claude Code, Cursor, GitHub
Copilot, or Codex. The harness registry lets each registered harness drive
the same `shipd` CLI from its own command palette. The `shipd harness` verb
family lists the registry and maintains the generated command files.

The command bodies scale to the harness. Each registry entry declares which
of four features its harness supports: `subagents`, `question-dialogs`,
`file-references`, and `background-tasks`. shipd renders one shared body per
command for each harness against that declaration. So a generated file never
mentions a feature its harness lacks.

Placement, file naming, and the frontmatter dialect follow each harness's own
convention. A harness that declares `subagents` also receives agent files
beside its commands.

## When to use it

- **Work in a harness other than Claude Code.** Generate the shipd commands
  into a repository, so that harness can run them.
- **Upgrade the generated commands.** Re-run `add` after a plugin update.
- **Check the installed files.** Report each harness's state with `status`.
- **Take the commands out again.** Remove the files shipd generated.

[`shipd install`](install.md) runs the user-global half for the harnesses a person picks.

## How to run it

1. List the registry, one line per harness:

   ```
   shipd harness
   ```

2. Inspect every field of one entry:

   ```
   shipd harness show <id>
   ```

3. From the repository root, generate the commands for one or more harnesses:

   ```
   shipd harness add <id>...
   ```

4. Check the generated files:

   ```
   shipd harness status
   ```

The `list` and `show` verbs change nothing.

### The ownership marker

Every generated file carries the ownership marker:

```
<!-- generated by shipd harness; do not edit -->
```

The marker keeps the other verbs safe:

- Re-running `add` is idempotent. Unchanged inputs leave every file
  byte-identical, so `add` also serves as the upgrade path.
- `add` refuses a target file without the marker, unless you pass `--force`.
- `remove` deletes only marker-carrying files, plus the directories it
  empties. It never deletes your own files.

`add` reports a harness with no surface for the selected mode as skipped.
The skip does not fail the run.

### Aider

Aider has no command files. `shipd harness add aider` writes one
ownership-marked `shipd-conventions.md` file, with shipd's conventions and its
command index. Wire it in through `read: shipd-conventions.md` in
`.aider.conf.yml`.

### The Claude Code plugin

The `s@shipd` plugin already provides the `/s:` commands to Claude Code. With
the plugin installed at user scope and enabled, `shipd install` writes no
Claude Code command or agent files. `shipd harness add claude-code --user`
writes none either. Both verbs retire the copies shipd wrote earlier.

## Reference

### Verbs

| Verb | Effect |
| --- | --- |
| `list` | Prints one line per harness. The default verb. |
| `show <id>` | Prints every field of one harness. |
| `add <id>...` | Writes the generated command files for each harness. |
| `remove <id>...` | Deletes the marker-carrying files for each harness. |
| `status [<id>...]` | Reports what is installed. It defaults to every harness. |

### Flags

| Flag | Effect |
| --- | --- |
| `--all` | Acts on every harness in the registry. |
| `--root DIR` | Names the repository to maintain. The default is the working directory. |
| `--user` | Acts on the user-global surfaces instead of the repository's. |
| `--force` | Acts on a target file this install does not own. |
| `--json` | Emits one JSON document on stdout instead of the text report. |
