# shipd — spec-driven development conventions

This repository uses **shipd**. Work is specified before it is written: a
request becomes checked-in artifacts — an idea, delta specs with `WHEN`/`THEN`
scenarios, and an ordered task list — and only then becomes code. The specs are
the contract; the implementation follows them, and the merged specs become the
repository's description of what it does.

Specs live in the content directory (`.shipd/` unless the repo's
`.shipd-config.json` renames it): `verified/` is the master library of current
capabilities, `planned/` holds changes in flight, and `completed/` holds the
ones already applied. One change is one worktree, one branch, and one pull
request.

## The loop

Every piece of work runs the same four beats, in order:

1. **plan** — investigate the code first, ask only what the repository cannot
   answer, then emit `plan.md`, `specs/<capability>/spec.md`, and `tasks.md`
   into the change's own directory. Planning ends at the artifacts; it never
   writes implementation code.
2. **gate** — the context gate promotes the change from `draft` to `ready`, or
   parks it at `rejected` with the specific gaps to close. A change never
   reaches `ready` by hand.
3. **build** — execute `tasks.md` one task at a time against the delta specs,
   checking off each task only when it is genuinely complete. Never guess a
   missing interface or an ambiguous requirement: ask instead.
4. **review** — a semantic review of the diff against the change's scenarios
   before anything is pushed, then merge and archive the change through the
   engine so the deltas land in `verified/`.

## Driving shipd from aider

- **Run the CLI and the engine scripts with `/run`.** Read-only reports are
  `/run shipd status`, `/run shipd list`, `/run shipd lint`; every lifecycle
  mutation is `/run python3 "$S/<script>.py" …` against the `$S` resolved
  above. Aider shows you the output and offers to add it to the chat — add it,
  since the next step usually depends on what it printed.
- **Read the artifacts into the chat rather than recalling them.** Start aider
  with `--read .shipd/planned/<change>/plan.md --read
  .shipd/planned/<change>/tasks.md`, or add them mid-session with
  `/read-only`, so the spec is context and not a paraphrase. Add the delta
  spec, `.shipd/planned/<change>/specs/<capability>/spec.md`, before
  implementing anything it governs.
- **Add only the files a task names to the edit set.** `/add` the files that
  task touches and `/drop` them when it is done; the task list already names
  them, so the edit set stays as small as the task.
- **Keep the artifacts out of the edit set.** The spec artifacts are the
  contract being implemented — hold them with `/read-only`, and change them
  only by re-running the planning workflow.
- **One change, one branch.** Work inside the change's worktree on its
  `change/<name>` branch, and let `/commit` cover one task's worth of work at a
  time.

## Wiring this file in

This file is generated. To have aider load it in every session, add it to
`.aider.conf.yml` at the repository root:

```yaml
read: shipd-conventions.md
```

Do not edit this file by hand — `shipd harness add aider` rewrites it, and
`shipd harness remove aider` deletes it. Everything durable belongs in the
specs.
