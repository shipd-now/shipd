# harness-docs
Status: verified
Epic: harness-install

## Idea

Document the harness mode — the interactive install finish, per-repo
`shipd harness add`, and the feature-scaling model — in the README and the
quickstart.

### Motivation

The `harness-install` epic ships an interactive `shipd install` finish and
generated per-harness command files, but no user-facing document mentions the
mode: the README's install documentation still ends at the launcher and
auto-update, and neither it nor `docs/quickstart.md` names `shipd harness add`
or the harness selection step.

### Details

- `README.md` install-mode docs gain the interactive finish: `shipd install`
  with the animated wordmark, the harness multi-select, the selection record,
  user-global generation, headless degradation, and re-run to reopen.
- `README.md` gains a labeled Harness mode subsection: generated `shipd-*`
  commands for the registry's twelve harnesses, the feature-scaling model,
  `shipd harness add`/`remove` for repositories, the inspection verbs, and the
  additive brand note.
- The README's CLI verb table gains a `shipd harness` row.
- `docs/quickstart.md`'s install step gains the selection step and a
  `shipd harness add` pointer.

Affected capabilities: `project-readme` (modified — one ADDED requirement).
Impact: `README.md`, `docs/quickstart.md`. Docs only — nothing under
`plugins/s/` changes, so no plugin version bump; the constitution's
engine-test rule binds engine scripts only, so no tests.

### Non-goals

- No changes to `install.sh`, the `shipd` binary, or any generated template —
  the sibling members (`install-tui`, `harness-verb`,
  `harness-command-bodies`) own those surfaces.
- No rewrite of the Skills table or the plugin's documented role — the plugin
  stays the engine's distribution vehicle; harness content is additive.
- No edits to `docs/getting-started.md` or `docs/what-is-shipd.md` — the
  member's scope is README + quickstart.
- No standalone harness guide document — the README subsection suffices at
  this size.

## Implementation

- **Facts trace to the epic's specs, never memory.** Every behavior claim
  comes from: `.shipd/verified/harness-registry/spec.md` (twelve harnesses,
  the four-feature vocabulary, `shipd harness`/`show` read verbs),
  `.shipd/verified/shipd-wordmark/spec.md` (TTY/`NO_COLOR`-gated animation),
  the ready sibling deltas
  `.worktrees/harness-verb/.shipd/planned/harness-verb/specs/harness-verb/spec.md`
  (ownership marker `<!-- generated by shipd harness; do not edit -->`,
  idempotent refresh, `--force`, `--user`, surface-less harnesses skipped)
  and
  `.worktrees/install-tui/.shipd/planned/install-tui/specs/install-tui/spec.md`
  (`/dev/tty` multi-select, `~/.shipd/harnesses.json` record, headless
  write-nothing exit-0 degradation, re-run preselects), plus the epic's
  Decisions in `.shipd/epics/harness-install/epic.md`. Rejected: waiting for
  the siblings to merge first — the approved epic delivers all members in one
  run; keeping claims at the level those requirement statements pin guards
  drift, and the PR's semantic review re-checks it.
- **Placement follows the install-section convention.** The interactive
  finish extends the existing "Install mode" subsection (it is part of the
  curl flow); the harness content is a new explicitly labeled `### Harness
  mode` subsection at the end of the Install section, after "Dev mode" —
  the same sibling-subsection pattern as "Per-repo mode" and "Dev mode".
  Rejected: a new top-level section after the CLI docs — harness mode is
  installation content and the `project-readme` ordering requirement keeps
  newcomer content before internals.
- **The CLI table gains only the `harness` row.** The table documents read
  verbs (`statusline`/`copilot`/`vendor` are section-documented, not table
  rows), so `harness` (list/show) joins the table matching `shipd --help`'s
  "the harness-adapter registry" line, while `shipd install` and
  `shipd harness add`/`remove` are documented in the install/harness
  subsections. Rejected: adding an `install` table row — it would break the
  table's read-verb scope.
- **Counts and wording follow the shipped registry.** The docs say **twelve**
  harnesses (the epic intro's "eleven" predates the registry splitting Cline
  and Roo Code); verified by running `./plugins/s/bin/shipd harness list`
  (exit 0, twelve rows). Command examples use the installed binary form in
  fenced blocks; tone and tense match the surrounding docs.
- **Brand note is one sentence, not a section.** The harness-mode subsection
  states the animated wordmark is confined to the install surface and ☕
  remains the brand mark everywhere it is spec'd — the epic's "Branding is
  additive" decision.
- Risk: a sibling delta could change before merge, staling a docs claim.
  Guard: claims are limited to the siblings' requirement statements (their
  stable contract), and the epic's per-PR semantic review plus the epic
  close-out catch any residual drift.
