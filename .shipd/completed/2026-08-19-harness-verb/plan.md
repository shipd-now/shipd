# harness-verb
Status: verified
Epic: harness-install

## Idea

Add the generation actions to the `shipd harness` verb — `add`, `remove`,
and `status` — rendering every command body through each registry dialect
into repo-level or user-global surfaces, ownership-marked and idempotent.

### Motivation

The registry and the body source exist (or are planned), but nothing writes
generated command files into a repository or a user-global directory — the
epic's per-repo integration path (`shipd harness add`, the fourth verb of
the `statusline`/`copilot`/`vendor` family) is unimplemented.

### Details

- New engine module `plugins/s/skills/build/scripts/harness_generate.py`:
  dialect rendering and the add/remove/status file operations.
- `plugins/s/bin/shipd`: `cmd_harness` gains `add`, `remove`, `status`
  actions (`--root`, `--user`, `--all`, `--force`, `--json` on `status`).
- Tests at `plugins/s/skills/build/tests/test_harness_generate.py`; plugin
  version bump.

Affected capabilities: `harness-verb` (added), `harness-registry` (modified
— the read-verbs requirement's read-only claim is scoped to the read
actions). Impact: the two files above plus
`plugins/s/skills/build/tests/test_harness_generate.py` and
`plugins/s/.claude-plugin/plugin.json`. Builds after
`harness-command-bodies` (imports `harness_bodies`); no new dependencies.

### Non-goals

- No interactive selection, no `~/.shipd/harnesses.json` consumption, and no
  `install.sh` wiring — that is the `install-tui` member (which will call
  this member's `--user` machinery).
- No body or registry content changes beyond consuming them.
- No network access, ever; no writes outside the managed surfaces.

## Implementation

- **Action surface:** `shipd harness add <id>... | --all [--root DIR]
  [--user] [--force]`, `shipd harness remove` (same selectors), and
  `shipd harness status [--root DIR] [--user] [id...] [--json]`. `add`/`remove`
  require at least one id or `--all` (usage error otherwise). Default
  target is repo-level at `--root` (default cwd, per `copilot`/`vendor`);
  `--user` targets the user-global `user_dir` surfaces instead. The epic's
  "report-only bare mode" is `status` — bare `shipd harness` already lists
  the registry (shipped), so the state report takes an explicit word,
  mirroring bare `shipd copilot`'s role.
- **What `add` writes per harness:** one file per command from
  `harness_bodies.commands()`, at `repo_pattern` (repo mode) or
  `user_dir + shipd-{command}.md`-style basename derived from the pattern
  (user mode; for Claude Code the `user_dir` already carries the `shipd/`
  namespace dir, so the basename is `{command}.md` — always the basename of
  `repo_pattern` when one exists, else `shipd-{command}.md`). Bodies are
  rendered with the harness's declared `features`. For a harness declaring
  `file-references`, the fallback reference files
  (`harness_bodies.reference`) are written under the refs root —
  `<content-dir>/harness/references/` in repo mode,
  `~/.shipd/harness/references/` in user mode — and `{refs}` is substituted
  with that root's path. A harness with no surface for the requested mode
  (aider everywhere; codex in repo mode; most harnesses in user mode) is
  reported `skipped (no <mode> surface)` and never an error.
- **Dialect rendering** (`harness_generate.py`): `yaml` emits `---`
  frontmatter carrying exactly the registry entry's `frontmatter` tuple,
  values from a fixed table — `name`: `shipd-<command>`; `description`:
  `harness_bodies.description(command)`; `id`: `shipd-<command>`;
  `category`/`tags`: `shipd`; `invokable`: `true`; `argument-hint`:
  `[input]`; `title`: `shipd-<command>`; a field with no table entry
  (`allowed-tools`) is omitted, documented in the module. Values are
  YAML-escaped (quoted when carrying `:` or leading specials).
  `markdown-headers` emits `# shipd-<command>`, the description line, a
  blank, then the body. The rendered body follows in both dialects.
- **Ownership:** every generated file's first body line (after frontmatter,
  or after the header block) is the marker
  `<!-- generated by shipd harness; do not edit -->`. `add` refuses an
  existing target file without the marker unless `--force`; with the marker
  it rewrites (byte-compare first, so re-runs are no-op idempotent).
  `remove` deletes only marker-carrying files and prunes directories it
  emptied; it never touches unmarked files without `--force`.
- **`status`:** per selected harness (default all), per surface, one of
  `installed` (all expected files present, byte-current), `stale` (present
  but differing from a fresh render), `foreign` (a target exists without
  the marker), `absent`. `--json` emits the same as one document. Changes
  nothing on disk.
- **Version bump:** `plugins/s/.claude-plugin/plugin.json` to the next
  patch above the branch's post-base-merge value.

Risk: the writing surface spans many directories — bounded by the managed
paths deriving only from registry data, the ownership marker, and tests that
run every action inside temp roots and isolated `HOME`s. Risk: this builds
before its `harness_bodies` import exists if ordered wrongly — the plan
binds the order (after `harness-command-bodies`), and the supersession
gate's base merge plus a loud import failure guard it.
