# harness-verb

### Requirement: Generation actions
id: harness-add-remove

The `shipd harness` verb SHALL provide `add` and `remove` actions taking one
or more harness ids or `--all`, a `--root DIR` (default: the working
directory) selecting repo-level surfaces, and `--user` selecting the
user-global surfaces instead. `add` SHALL write one generated command file
per body-template command into the harness's registry-declared surface
(`repo_pattern` under the root, or the `user_dir` with the pattern's
basename — `shipd-{command}.md` where no pattern exists), rendering each
body with the harness's declared features, and for a harness declaring
`file-references` SHALL also write the fallback reference files under the
refs root (`<content-dir>/harness/references/` in repo mode,
`~/.shipd/harness/references/` in user mode), substituting `{refs}` with
that root. Every generated file SHALL carry the ownership marker
`<!-- generated by shipd harness; do not edit -->`. If a target file exists
without the marker, then the action SHALL refuse it with a single
`Error: <reason>` line unless `--force`. Re-running `add` with unchanged
inputs SHALL leave every file byte-identical (idempotent). `remove` SHALL
delete only marker-carrying files and directories it thereby empties. A
harness with no surface for the selected mode SHALL be reported as skipped
and SHALL NOT fail the action. The actions SHALL never access the network.

#### Scenario: Add generates owned files for a repo-level harness
- **WHEN** `shipd harness add cursor --root <tmp>` runs in a temp repo
- **THEN** `.cursor/commands/` under the root holds one `shipd-<command>.md`
  per body template, each carrying the ownership marker and cursor's
  frontmatter fields, and re-running the command changes no bytes

#### Scenario: File-references harnesses get reference files
- **WHEN** `shipd harness add cursor --root <tmp>` runs
- **THEN** the fallback reference files exist under the root's
  `<content-dir>/harness/references/` and the generated bodies point at
  that root where their `{refs}` placeholder stood

#### Scenario: User mode writes the user-global surface
- **WHEN** `shipd harness add codex --user` runs with an isolated `HOME`
- **THEN** the generated files land under `~/.codex/prompts/` and nothing
  is written under the working directory

#### Scenario: A modeless harness is skipped, not failed
- **WHEN** `shipd harness add aider cursor --root <tmp>` runs
- **THEN** the exit code is 0, cursor's files are generated, and the output
  reports aider as skipped with no aider file written

#### Scenario: Foreign files are refused without force
- **WHEN** a target path exists without the ownership marker and
  `shipd harness add` runs without `--force`
- **THEN** a single `Error: ` line names the file, the exit code is
  nonzero, and the file is unchanged

#### Scenario: Remove deletes only owned files
- **WHEN** `shipd harness remove cursor --root <tmp>` runs after an `add`
  and one unmarked file was placed in the same directory
- **THEN** the generated files are gone, the unmarked file remains, and
  directories emptied by the removal are pruned

### Requirement: Installation state report
id: harness-status

The `shipd harness` verb SHALL provide a read-only `status` action taking
optional harness ids (default: all), `--root DIR`, `--user`, and `--json`,
reporting
per harness and surface one of `installed` (every expected file present and
byte-identical to a fresh render), `stale` (present but differing),
`foreign` (a target exists without the ownership marker), or `absent`. The
action SHALL create or modify no files.

#### Scenario: Status reflects the lifecycle
- **WHEN** `status` runs before an `add`, after it, and after one generated
  file is edited in place
- **THEN** the harness reports `absent`, then `installed`, then `stale`,
  and the temp root's contents are unchanged by every `status` run

#### Scenario: JSON status is machine-readable
- **WHEN** `shipd harness status --root <tmp> --json` runs
- **THEN** stdout parses as one JSON document keyed by harness id

### Requirement: Dialect rendering
id: dialect-rendering

The generation SHALL render each harness's files per its registry dialect:
`yaml` emits `---`-delimited frontmatter carrying exactly the entry's
declared `frontmatter` fields with the fixed value table (`name`/`id`/
`title`: `shipd-<command>`; `description`: the body template's declared
description; `category`/`tags`: `shipd`; `invokable`: `true`;
`argument-hint`: `[input]`; an undeclared-value field is omitted), values
escaped for YAML; `markdown-headers` emits a `# shipd-<command>` heading and
the description line instead of frontmatter. In both dialects the rendered
body follows, and the file extension comes from the surface pattern.

#### Scenario: YAML dialect carries the declared fields
- **WHEN** cursor's `shipd-plan` file is generated
- **THEN** its frontmatter contains exactly `name`, `id`, `category`, and
  `description` with `name: shipd-plan`, and the github-copilot variant of
  the same command carries only `description`

#### Scenario: Markdown-headers dialect carries no frontmatter
- **WHEN** cline's `shipd-plan` file is generated
- **THEN** it contains no `---` frontmatter block and begins with
  `# shipd-plan` followed by the description
